Field Notes on Reliable Agents (1): The Build Is the Only Gate

When you run a swarm of agents that edit real code, every agent will tell you its piece compiles. That's not the question. The only acceptance test is whether the whole system still builds and runs — here's why, and how to enforce it.

I run a lot of long-lived agent loops — pipelines where a parent agent spawns children, each child edits a slice of a codebase, and the parent stitches the results back together. The single most expensive lesson I’ve learned is embarrassingly simple: a component reporting “green” tells you almost nothing about whether the system works.

This is the first of seven field notes on keeping such systems honest. They’re deliberately generic — none of them depend on a particular framework or model. This one is the foundation the other six build on.

The failure mode: green pieces, broken whole#

Here’s the shape of the disaster. A parent agent hands out three tasks. Each child agent edits its files, runs a local check — a type-check on the files it touched, a unit test for its module — sees green, and reports success. The parent collects three “done"s and declares victory.

Then you actually build the thing, and it doesn’t compile.

How? A child added an import that resolves fine in isolation but collides with a symbol another child renamed. A shared interface gained a field in one file and lost it in another. A config value one agent removed is still referenced three modules away. Every child was locally correct. The integration was globally broken. And because each child only checked its own slice, nobody was looking at the seam where the breakage lived.

The insidious part is that the per-agent checks weren’t wrong — they were just answering a narrower question than the one that matters. “Does my file type-check?” is not “does the project build?” The gap between those two questions is exactly where multi-agent work goes to die.

The rule: the orchestrator’s real build is the gate#

So the rule I now enforce without exception:

The only signal that counts is the orchestrator running the real build and the real smoke test, end to end, after all the pieces have landed. Per-agent checks are hints, not acceptance.

Concretely, the parent agent’s workflow looks like this:

1. spawn children, collect their diffs
2. apply all diffs to one working tree
3. run the actual production build command
4. run a minimal smoke test (does the thing start? does one real request return 200?)
5. ONLY NOW is the batch "done"

Steps 3 and 4 are non-negotiable and they belong to the parent, not the children. A child cannot verify integration because a child cannot see the integration. Only the orchestrator holds the merged state, so only the orchestrator can test it.

This sounds obvious written down. In practice, the pull toward trusting the children is strong — they’re right there telling you they succeeded, and re-running a full build is slow and sometimes painful. That pull is the trap.

Why “slow and painful” is not an excuse#

The most common objection is cost. Full builds are slow. On a memory-constrained machine a build can thrash for twenty minutes, or fall over entirely. Surely we can skip it when the changes are “obviously safe”?

No. But you can be smart about batching.

The trick is to separate the frequency of the gate from the frequency of the changes. Don’t build after every single edit — batch several changes and pay for one build. If four agents each made a small, prompt-only tweak, apply all four, then build once. You amortize the cost of the gate across the batch instead of paying it per change.

What you must never do is skip the gate because the batch “feels safe.” The whole reason integration bugs are dangerous is that they don’t feel dangerous from inside any single change. The feeling of safety is generated by looking at one slice; the bug lives in the seam you’re not looking at.

There’s a second reason to respect the build even when it’s expensive: a fragile build is itself a signal. If your acceptance gate keeps falling over, that’s telling you the system is too tightly coupled or under-resourced. Papering over it by skipping verification just moves the failure downstream, where it’s more expensive to find.

Distinguishing a slow build from a stuck build#

If you’re going to make the build your gate, you need to know the difference between “slow” and “hung” — otherwise you’ll kill healthy builds out of impatience and cargo-cult a restart ritual that doesn’t help.

On one constrained box I watch three signals to tell them apart:

  • A healthy slow build: a worker process pegging CPU, swap usage low and stable, and — crucially — the output directory eventually exploding with files as the compiler reaches its finalize phase. This looks alarming (nothing visible for minutes) but it’s working. Wait it out.
  • A genuinely stuck build: zero file writes, swap climbing steadily toward the ceiling, available memory collapsing. That’s thrash, not progress. Kill it, reclaim resources, retry with more headroom.

The general principle: before you intervene in a long-running step, measure what it’s actually doing. “It’s taking a while” is not a diagnosis. Look at whether it’s making progress on some observable axis (files written, CPU burned productively, log lines advancing). Impatience that kills healthy work is its own reliability bug.

A cheaper gate for deterministic code#

The build is the gate for integration. But some changes are to pure, deterministic logic — a rule engine, a scanner, a parser, a scoring function. For those, there’s a second, cheaper gate worth adding before the expensive build.

When I change a deterministic function, I run a tiny self-test right there: feed it three inputs with known outputs.

  • One input that should trigger the behavior (a true positive)
  • One input in a context that should not trigger it (a guarded false positive)
  • One input exercising whatever I just added (the new case)

This catches logic regressions — an over-eager guard that now suppresses real hits, a new rule that never fires — far faster than a full build, and far more precisely than a type-check, which only proves the code is well-formed, not that it’s correct. Type-checking tells you the shape is right; a three-case self-test tells you the behavior is right. For deterministic code, that second question is the one that bites you.

The through-line#

All six of the notes that follow are, in some sense, variations on this one. Reliability in agent systems is almost never about making a single step smarter. It’s about being disciplined about what counts as done — refusing to accept a narrower, cheaper signal in place of the real one, even when the real one is slow, even when every piece swears it’s fine.

The children will always tell you they succeeded. Your job as the orchestrator is to not believe them until the whole thing builds and runs.

What’s next#

The next note is about the mirror image of this problem: what to do when your acceptance signal itself is unreliable — when the thing telling you “it’s visible” or “it’s done” is a probabilistic observer that sometimes silently lies. The answer is deterministic safety nets, and it’s saved me from more invisible-failure bugs than anything else.
