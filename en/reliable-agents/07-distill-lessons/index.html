Field Notes on Reliable Agents (7): Turn Every Scar Into a Rule

The final discipline that makes all the others compound: after every fix, distill the lesson into a form the system itself can consume — a test, a scan rule, a safe-pattern — so the scar becomes automation that prevents the next occurrence, instead of tribal knowledge you re-learn the hard way.

Every lesson in this series started the same way: something broke, I diagnosed it, I fixed it. That’s the normal loop, and most people stop there. This final note is about the step after the fix — the one that turns a private scar into a permanent property of the system, so nobody (including future-you) has to bleed for it twice.

I think of it as apprenticeship in reverse. A master teaches an apprentice not just what to do but how to judge when to do it. When you fix something, you’ve just learned a judgment. The question is: can you teach that judgment to the system, so the system makes the right call next time without you?

The waste of a lesson that lives only in your head#

A fix that isn’t distilled decays in a predictable way. You fix a subtle bug — say, a counter that must be reset before a call, not after. You understand it deeply, in the moment. Six weeks later, in a different module, you (or an agent, or a teammate) write the same after-the-call reset, because the understanding lived in your head and your head has moved on.

The knowledge existed. It just wasn’t where the next mistake would happen. That’s the core waste: lessons stored in conversation context, or in one person’s memory, are not present at the point and time of the next occurrence. They may as well not exist.

So the discipline is: after fixing something, ask “what would have caught this automatically, and can I add it?” Not “what did I change” — that’s just the diff. The valuable artifact is the rule that would have prevented the class of bug, placed where it will fire next time.

Distill the decision logic, not the diff#

Here’s the part people get wrong: they record what changed instead of how to decide. “Changed line 42 to reset before the call” is a diff — it helps with this bug and no other. What a system can actually learn from is the decision logic: “State that must be clean at the start of an operation should be initialized at the start of that operation, not at the end of the previous one — because cleanup-on-success leaks whenever success doesn’t happen.”

The second form generalizes. It can become a code-review checklist item, a lint rule that flags reset-after-call patterns, a note an agent reads before touching counter logic anywhere. The diff can’t do any of that; it’s too specific. When you distill a lesson, capture the pattern → diagnosis → fix triple, and especially the why and the how to judge the edge cases — because that’s what lets the rule apply to situations you haven’t seen yet.

This is why, throughout this series, I’ve stated each lesson as a principle with a reason attached, not as a recipe. “Charge before you produce, because a crash between produce and charge is silent margin loss.” The reason is what makes the rule portable to a new situation where the recipe doesn’t literally apply.

Feed the lesson to whatever enforces things automatically#

The highest form of this discipline is handing the lesson to a component that acts on it without you. Depending on your system, that’s a different artifact:

  • If you have a test suite: the moment you fix a bug, add a regression test that encodes its signature — an input that triggers the class of bug, asserting the correct behavior. Now the lesson runs on every change, forever, unattended. The bug can come back, but it can’t come back silently.
  • If you have any static analysis or scanning: turn the pattern into a rule. A lint rule for the reset-after-call shape. A scan for read paths that touch compensable data without filtering the marker. The rule finds the next instance before it ships.
  • If you have an autonomous improvement component — something that proactively scans for issues and proposes or applies fixes — teach it the pattern in the form it consumes: a backlog item, a scan signature, a safe-transformation. Then verify it can actually pick up and apply the pattern on its own. (And per note four: confirm it runs on the real path, not just that you added it.)
  • If you have none of those: at minimum, write the lesson down where the next person doing this work will actually see it — a document colocated with the code, not a message in a chat that scrolls away. The bar is “present at the point of the next mistake,” and a searchable note near the code clears it; a conversation does not.

The through-line: move the lesson as close as you can to automatic enforcement. A test that runs on every commit beats a checklist item a human might skip beats a note someone might read beats knowledge in one head that’s already forgetting it.

The compounding#

Here’s why this last discipline is the one that makes the other six worth anything. Each of the earlier notes is a lesson I paid for once. In isolation, each is worth exactly one avoided bug. But distilled into the system — as tests, as scan rules, as principles an agent consults — each lesson stops being a one-time save and becomes a permanent floor the system can’t fall below.

That’s the difference between a system that gets more reliable over time and one that just accumulates the same failures in new costumes. A reliability discipline that isn’t captured degrades to folklore. Captured, it compounds: round 30 is genuinely safer than round 3, not because the people got smarter, but because thirty scars became thirty rules the system now enforces on its own.

Build the gate. Net the flaky observers. Charge before you produce. Verify it runs, not that it deployed. Keep autonomy on recorded identities. Re-verify the old fixes. And then — the step that makes all of it durable — turn every one of those hard-won judgments into something the system enforces without you.

Where to go from here#

There’s no single trick in this series, and that’s the point. Reliable agent systems come from a stack of small disciplines about what counts as done — and from the meta-discipline of turning each lesson into automation so the stack keeps growing. Pick the one failure mode you recognize most from your own systems, add the one guard that would have caught it, and encode it so it can’t come back quietly. Then do it again next time something breaks. That loop, run patiently, is the whole method.
