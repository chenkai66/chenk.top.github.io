Field Notes on Reliable Agents (2): Safety Nets Beat Flaky Observers

Probabilistic triggers — IntersectionObservers, LLM judgments, event listeners — fail silently and leave you with invisible content or stuck state. The fix is a deterministic fallback behind every unreliable observer, plus one hard rule: the rendered output is ground truth, not the observer's opinion.

The first note argued that the build is the only acceptance gate. This one is about what happens when the observer — the thing that’s supposed to tell you a piece of work landed — is itself unreliable. Because sometimes the code is correct and the trigger that’s supposed to activate it just… doesn’t fire.

I lost a genuinely embarrassing amount of time to a bug in this family, so this note is mostly a scar.

The invisible-content bug#

I had a page that revealed its content on scroll: each card starts hidden and fades in when it enters the viewport. The mechanism was an IntersectionObserver — watch each card, add a “visible” state when it crosses into view. Clean, standard, works in the demo.

In production, the top two-to-four cards stayed at opacity: 0. Invisible. A blank void where content should be.

Here’s the part that cost me the most: when I inspected the DOM, everything looked fine. The right number of cards were present. No layout gaps. The markup was correct. Every automated check I ran against the structure said “healthy page, all cards present.” Meanwhile a human looking at the actual rendered page saw a hole.

The observer had silently failed to fire for the cards that were already near the top of the viewport at load time — a known sharp edge of that API. The cards existed; they were just permanently transparent. And no DOM-level assertion catches “present but invisible,” because presence and visibility are different properties, and the cheap check only looked at the first one.

Lesson one: the rendered output is ground truth#

The DOM said one thing. The screenshot said another. The screenshot was right.

This generalizes far beyond web pages. Whenever you verify a probabilistic or event-driven system, there’s a temptation to check the proxy that’s easy to query — the DOM node count, the “task marked done” flag, the log line that says “handler registered” — instead of the actual outcome you care about. The proxy is cheaper and it’s usually correlated with success. Until it isn’t, and then it lies to you with total confidence.

The rule I now hold: verify the thing you actually care about, in the form the user experiences it. For a visual change, that means a screenshot, not a DOM query. For a “the data got written” claim, that means reading the row back, not trusting the write call’s return value. For “the agent finished the task,” that means checking the artifact it was supposed to produce, not the status field it set on itself.

An even sharper version, which I had to learn the hard way on this same bug: don’t measure mid-transition. My first “fix verification” checked opacity while the fade animation was still running, and got garbage readings that changed every time I re-ran it. Ground truth is the settled state — wait past the animation, the stagger delay, and any safety timers before you decide what you’re looking at.

Lesson two: put a deterministic net under every probabilistic trigger#

Fixing the verification tells you when you’re broken. It doesn’t stop you breaking. For that, the pattern is a deterministic fallback layered under the flaky trigger.

The observer is an optimization: it reveals things at the perfect moment, lazily, efficiently. But its job — “make sure every card eventually becomes visible” — has a much dumber, more reliable implementation. So I now run both:

1. the IntersectionObserver (the fast, precise path)  — fires per-card as they enter view
2. a scroll-event listener                             — re-checks on any scroll
3. a one-shot safety timer (~1.2s after load)          — force-reveals anything still hidden

Layers 2 and 3 are the net. If the observer misses a card, the scroll listener catches it the moment the user moves. If the user never scrolls (the top cards, exactly the failing case), the timer sweeps in after a beat and force-reveals everything still stuck. The precise path handles the common case efficiently; the dumb paths guarantee the invariant — everything becomes visible — no matter what the observer does.

Two implementation details that matter:

  • Make the reveal idempotent. All three layers may try to reveal the same element. The operation must be safe to run twice — set-to-visible, not toggle — or the layers fight each other.
  • Widen the observer’s own margins first. Before adding the net, I set the observer’s root margin generously (fire well before the element is actually on screen) and its threshold to zero (fire on the first pixel). That alone fixes most misses; the net is for the rest.

Where this pattern shows up beyond the browser#

This isn’t a front-end trick. The same shape appears everywhere a probabilistic or best-effort mechanism gates something that must happen:

  • An LLM deciding whether a task is complete. Useful, but sometimes wrong. Put a deterministic post-check under it: does the required output actually exist and parse?
  • An event/webhook that’s supposed to advance a workflow. Events get dropped. Add a periodic sweep that finds anything stuck in an intermediate state past a timeout and pushes it forward.
  • A cache/CDN that’s supposed to have picked up your new content. Don’t trust “I deployed.” Fetch the live asset and compare its content hash to what you built. (Content-fingerprinted filenames make this trivial: the live filename literally is the hash.)

The unifying principle: anything probabilistic that guards an invariant needs a deterministic backstop, and the backstop should assert the invariant directly — “the thing is visible,” “the row exists,” “the workflow advanced” — not the proxy that’s easy to poll.

The cost, honestly#

The net isn’t free. You’re running redundant work — a scroll handler that mostly finds nothing to do, a sweep that usually sweeps nothing, a hash comparison that usually matches. That’s the point. The redundancy is cheap and constant; the failure it prevents is rare and catastrophic (invisible content in production that your automated checks swear is fine). That’s a trade I take every time.

There is one thing to watch: don’t let the net paper over a broken precise path. If your safety timer is doing all the work because the observer never fires at all, you haven’t added resilience — you’ve just moved to a slower, dumber mechanism and hidden the regression. Log when the net catches something. If it’s catching things constantly, the fast path is broken and the net is masking it.

What’s next#

The next note moves from “did it happen” to “did it happen exactly once, in the right order.” When an agent step costs money or mutates shared state, the ordering of your writes decides whether a crash mid-step loses money, double-charges, or stays clean. The pattern is charge-before-you-produce, and it’s mostly about being paranoid in the right sequence.
