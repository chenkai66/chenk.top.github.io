Field Notes on Reliable Agents (4): Deployed Is Not Executed

The most seductive lie in shipping software: 'I deployed it, so it works.' Code can ship, sit there, and never run on the path you think it runs on. Two failure modes — built-but-not-wired, and deployed-but-not-executed — and how to prove the feature actually fires.

CK
Chen Kai May 8, 2026 · 10 min read · 1013 words
#agents#reliability#verification#wiring
阅读中文版 →

There’s a specific flavor of self-deception that shows up once your changes get big enough to have plumbing. You write a feature. You deploy it. The deploy succeeds. You mark it done. And it never runs — not because it’s broken, but because nothing actually calls it on the path you care about.

I’ve shipped this bug enough times that I now treat “deployed” and “working” as unrelated facts until proven otherwise. This note is about the two ways the gap opens, and how to close each.

Failure mode one: built but not wired#

The backend supports the feature. The function exists, it’s correct, it’s even tested. But the thing that’s supposed to use it doesn’t — the caller hardcodes the old value, or reads a field that the new code never populates, or the UI has a dropdown with the new option missing.

The sharpest version I’ve hit: a data pipeline was upgraded to compute several new fields. The computation was correct. But the assembly step that builds the final result object did an explicit field-by-field mapping — and nobody added the new fields to that mapping. So the pipeline dutifully computed them and then silently dropped them on the floor at the last step. Every individual piece was right. The feature was invisible because one glue layer never learned about it.

This is high-value to catch because the fix is usually tiny (add three lines to the mapping) and the payoff is large (a whole feature that was doing nothing now works). But you only find it if you trace the value end to end — from where it’s produced to where it’s actually consumed and displayed. “The function returns the right thing” is not enough; you have to follow the thing all the way to the surface.

The habit: when you add a capability, trace it to the point of use, not just the point of production. Ask “who reads this, and did I update every reader?” — the same totality discipline from the compensation-marker rule in the previous note. Backend-supports-it plus UI-hardcodes-it equals a feature nobody can reach.

Failure mode two: deployed but not executed#

The wiring is fine. The code ships. But it still doesn’t run, because the path you think exercises it isn’t the path production takes.

The config flag defaults off. The new branch is behind a condition that’s never true in the real environment. The scheduled job is registered but the scheduler only fires when the process is idle, and yours never is. The handler is installed but the event that triggers it gets filtered upstream. In every case: present, correct, deployed — and cold. Zero executions.

The only cure is to observe the code actually running on the real path. Not “it’s deployed.” Not “the tests pass.” A log line, a metric increment, a side effect you can see, produced by the production trigger doing the production thing. If you can’t point at evidence that the code path fired in the real environment, you haven’t verified it — you’ve verified it exists.

For anything I genuinely care about, I add a cheap, greppable signal — a log line the first time the new path executes — and then I go make the real trigger happen and confirm the line appears. It feels redundant right up until the day it reveals that your carefully-shipped feature has run exactly zero times since launch.

Verifying propagation without fooling yourself#

A specific, common instance: you push a change through a build-and-deploy pipeline that sits behind a cache or CDN, and you want to confirm the new version is actually live, not a stale cached copy.

The naive check — “does the page contain my new text?” — is fragile. Caches serve stale copies, and worse, if your build minifies output it may strip the exact string you’re grepping for (comments vanish, whitespace collapses, identifiers get mangled). You grep for something that got optimized away and conclude, wrongly, that the deploy failed.

Two techniques that actually work:

  • Grep for a string literal that survives optimization, not a comment or a variable name. Minifiers preserve user-facing strings and certain literals; they delete comments and rename locals. Choose your needle accordingly.
  • Better: compare content hashes. If your build tool fingerprints output filenames by content (common in modern asset pipelines), then the live filename is the hash of the content. Fetch the live page, read which asset filename it references, and compare that hash to the one your local build produced. Match means the live site is serving exactly your bytes. This is immune to caching lies and minification — it’s comparing identities, not searching for substrings.

The general principle, again: verify the outcome you care about in a form that can’t be faked by an intermediate layer. “The text is there” can be faked by a stale cache. “The content hash matches” cannot.

Why this keeps happening#

The reason deployed-isn’t-executed is such a persistent trap is that every intermediate success is real. The build really did succeed. The deploy really did complete. The function really is correct. Each green light is telling the truth about its own narrow scope. What no single green light asserts is the end-to-end claim you actually care about: this capability changes what a real user experiences on the real path.

That’s the same disease as note one (green pieces, broken whole) and note two (proxy metric vs. real outcome), viewed from the shipping end. The cure is always the same shape: refuse to accept a chain of local successes as proof of the global outcome. Follow the thing to where it’s used. Watch it fire on the real path. Compare identities, not proxies.

What’s next#

The next note is about letting agents act on their own — autonomous cleanup, self-healing, auto-remediation — without letting them nuke the wrong thing. The tension is real: autonomy is the entire point, but an agent confidently deleting based on a bad inference is worse than no automation at all. The resolution is trust-but-verify, and deleting only by exact recorded identity.
