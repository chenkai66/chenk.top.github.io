Field Notes on Reliable Agents (6): Re-Verify the Old Fixes Every Round

In a long-running optimization loop, the most dangerous regression is the one that quietly re-breaks something you already fixed. The habit that prevents it: every round, re-verify the prior fixes on their real trigger paths — not just the new change.

#agents#reliability#regression#verification
阅读中文版 →

If you run a system in a continuous improvement loop — round after round of “find something to make better, change it, verify, repeat” — you eventually hit a specific, demoralizing failure: a change in round 20 quietly re-breaks something you carefully fixed in round 8. Everyone was watching the new change. Nobody was watching the old guarantee. And because the old fix had been working for twelve rounds, it wasn’t on anyone’s mind.

This note is about the habit that prevents that: each round re-verifies the prior fixes, on their real trigger paths, not just the new change.

Why old fixes rot#

A fix isn’t a permanent property of the system. It’s a local arrangement that holds given everything else staying put. When you change something else, that arrangement can quietly come apart.

The concrete ways this happens are mundane and endless. A later change reintroduces the exact override you removed. A refactor moves code out from under the condition that was protecting it. A new feature adds a fourth read path that forgets the compensation marker you added to the first three. A dependency bump changes a default you were relying on. None of these look like “re-break the old fix” from inside the change that causes them — they look like unrelated progress. That’s exactly why they slip through.

There’s a temporal illusion at work: the longer a fix has held, the safer it feels, and the less you check it. But a fix that’s held for twelve rounds is not more robust than one that held for one round — it’s just had more opportunities to be silently undone, none of which you were looking for.

The habit: verify the invariant, not the diff#

The fix is to stop thinking of verification as “check the thing I just changed” and start thinking of it as “check that the invariants still hold.” Each round, before declaring the round done, re-run the checks that established your earlier guarantees — and re-run them the way that actually exercises the guarantee, on the real trigger path.

That last clause is the whole game. It’s not enough to re-run a shallow check. If round 8 fixed “content becomes visible on scroll,” then re-verifying it means loading the real page and confirming the content actually renders — the screenshot, per note two — not checking that a config value is still set. Verify the invariant in the form it matters, on the path that would break it.

A worked example from a visual system I iterate on: several rounds fixed different rendering guarantees — cards become visible, heights stay equal, text stays legible. Now every round, part of “done” is re-loading the real pages and confirming all those still hold, because a CSS change made for one reason routinely threatens a guarantee established for another. The cost is a few minutes of re-checking per round. The alternative is discovering, five rounds later, that something’s been broken the whole time and shipping the breakage repeatedly.

Ground truth over reported state, again#

This connects straight back to note two, and it’s worth stating as its own rule because the loop makes it so tempting to violate. When you re-verify old fixes, verify against ground truth, not against what the system reports about itself.

In one loop I kept getting contradictory readings from a fix-verification check that measured an intermediate, transient value — the check said the fix was broken, then fine, then broken, changing every time I ran it. The temptation was to keep tweaking the fix in response to the flapping check. The check was the problem: it was measuring mid-transition, so it was noise, not signal. Ground truth — the actual rendered, settled output — showed the fix was fine the whole time.

The rule: when a verification check gives unstable or contradictory results, suspect the check before you suspect the fix. A flapping signal is often measuring the wrong thing, or measuring at the wrong moment. Re-verification is only useful if the re-verification itself is measuring ground truth. A flaky re-check that panics you into “fixing” working code is worse than no re-check at all.

Make the re-verification cheap, or it won’t happen#

There’s an honest tension here. Re-verifying every prior guarantee every round is, in the limit, unbounded work — round N would re-check N-1 previous fixes. That doesn’t scale, and if the re-check is expensive, you’ll skip it exactly when you’re busy, which is exactly when you’re most likely to break something.

Two ways to keep it affordable:

  • Batch the invariants into one cheap sweep. Instead of N separate checks, maintain a single “does everything still hold” pass — load the real pages, assert all the current invariants at once. One screenshot can verify several visual guarantees simultaneously. One smoke test can exercise several code paths. Amortize.
  • Promote the recurring ones to permanent tests. If a guarantee keeps almost-breaking, it doesn’t belong in a manual per-round checklist — it belongs in an automated regression test that runs every time, unattended. Which is precisely the subject of the final note: turning a lesson you keep re-applying by hand into something the system enforces on its own.

The re-verification you actually do is worth infinitely more than the thorough one you skip because it’s too slow. Make it cheap enough that skipping it never feels tempting.

What’s next#

The final note ties the whole series together. Every lesson in these six notes started as a scar — something broke, I diagnosed it, I fixed it. The waste is re-learning the same scar next month. The last note is about the discipline of distilling each failure into a rule the system itself can consume: a test, a scan rule, a safe-pattern — so the lesson outlives the conversation that taught it.
