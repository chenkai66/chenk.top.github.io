让 Agent 靠谱起来（6）：每一轮都重新验证旧的修复

在一个长期运行的优化循环里，最危险的退化，是那个悄悄把你早就修好的东西又弄坏了的退化。防住它的习惯：每一轮，都在真实触发路径上重新验证之前的修复，不只是那个新改动。

如果你把一个系统跑在持续改进的循环里（一轮又一轮"找点能变好的、改它、验证、重复"），你迟早会撞上一个特定的、让人泄气的故障：第 20 轮的一个改动，悄悄把你在第 8 轮精心修好的东西又弄坏了。所有人都在盯着那个新改动。没人在盯着那个旧保证。而且因为那个旧修复已经好好工作了十二轮，它根本不在任何人的脑子里。

这一篇讲防住这事儿的习惯：每一轮都在真实触发路径上重新验证之前的修复，不只是那个新改动。

旧修复为什么会烂#

一个修复不是系统的一个永久属性。它是一个局部安排，成立的前提是别的一切都待着不动。当你改了别的东西，那个安排就可能悄悄散架。

它发生的具体方式平淡又无穷。一个后来的改动，重新引入了你移除过的那个 override。一次重构，把代码从保护它的那个条件底下挪了出去。一个新功能加了第四条读路径，忘了你给前三条加的补偿标记。一次依赖升级，改了一个你正靠着的默认值。从造成它们的那个改动内部看，这里没有一个看着像“把旧修复又弄坏了”，它们看着像不相关的进展。这恰恰是它们溜过去的原因。

这里有个时间错觉在作祟：一个修复撑得越久，感觉越安全，你也越少去查它。但一个撑了十二轮的修复，并不比一个撑了一轮的更健壮，它只是有了更多次被悄悄撤销的机会，而这些机会你一次都没在找。

习惯：验证不变式，不是验证 diff#

修法是别再把验证想成"查我刚改的那个东西"，改成想成"查那些不变式是不是还成立"。每一轮，在宣布这一轮完成之前，重新跑一遍当初建立你更早那些保证的检查，而且要用真正演练那个保证的方式去跑，走真实触发路径。

最后这半句是全部的关键。重跑一个浅检查是不够的。如果第 8 轮修的是"内容随滚动变可见"，那重新验证它就意味着加载真实页面、确认内容真的渲染出来（截图，见第二篇），而不是查一个配置值是不是还设着。以它真正重要的形态、在会弄坏它的那条路上，去验证这个不变式。

一个我在迭代的视觉系统里的实例：好几轮分别修了不同的渲染保证（卡片变可见、高度保持相等、文字保持可读）。现在每一轮，“完成"的一部分，就是重新加载真实页面、确认所有这些仍然成立，因为一个出于某个理由做的 CSS 改动，会例行地威胁到一个出于另一个理由建立的保证。代价是每轮几分钟的重查。另一条路，是五轮之后才发现某个东西一直坏着、而你已经把这个破坏反复发布了很多次。

再一次，真值高于报告的状态#

这直接连回第二篇，而且值得单列成一条规则，因为循环让违反它变得太诱人。当你重新验证旧修复时，拿真值去验证，别拿系统对自己的报告去验证。

在一个循环里，我一直从一个修复验证检查那儿拿到互相矛盾的读数，那个检查测的是一个中间的、瞬时的值：检查一会儿说修复坏了、一会儿说没事、一会儿又说坏了，每次跑都变。诱惑是跟着这个抖动的检查不停去调那个修复。问题出在检查身上：它在过渡进行中测量，所以它是噪声，不是信号。真值（实际渲染出来、沉降后的结果）显示这个修复自始至终都没问题。

规则是：当一个验证检查给出不稳定或矛盾的结果，先怀疑检查，再怀疑修复。 一个抖动的信号，往往是在测错的东西、或者在错的时刻测。重新验证只有在它本身测的是真值时才有用。一个抖动的重查，把你吓得去"修"一段本来好好的代码，比完全不重查还糟。

让重新验证足够便宜，否则它不会发生#

这里有个诚实的张力。每一轮都重新验证之前每一个保证，在极限上是无界的工作量，第 N 轮要重查 N-1 个之前的修复。这不 scale，而且如果重查很贵，你会恰好在忙的时候跳过它，而那恰好是你最可能弄坏东西的时候。

两个办法让它保持负担得起：

  • 把不变式批成一次便宜的扫描。 不要 N 个分开的检查，维护一个"是不是一切都还成立"的单次遍历：加载真实页面，一口气断言所有当前的不变式。一张截图能同时验证好几个视觉保证。一个冒烟测试能演练好几条代码路径。摊薄。
  • 把反复出现的那些提升为永久测试。 如果一个保证总是差点坏，它就不该待在一个手工的、每轮的清单里，它该待在一个每次都无人值守自动跑的回归测试里。这恰好是最后一篇的主题：把一个你老是靠手重新应用的教训，变成系统自己去执行的东西。

你真正做了的那个重新验证，比你因为太慢而跳过的那个彻底验证，值无穷多倍。让它便宜到跳过它从来不诱人。

接下来的内容#

最后一篇把整个系列系到一起。这六篇里的每一个教训，一开始都是一道疤：某个东西坏了、我诊断了它、我修了它。浪费在于下个月把同一道疤再学一遍。最后一篇讲把每次故障蒸馏成一条系统自己能消费的规则的那份纪律：一个测试、一条扫描规则、一个安全模式，好让教训活得比教会它的那次对话更久。
