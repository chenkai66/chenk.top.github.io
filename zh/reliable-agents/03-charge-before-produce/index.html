让 Agent 靠谱起来（3）：先扣费，再产出

当一个 agent 步骤要花钱、或者要改共享状态，你写入的顺序比那一步本身更重要。先扣费再产出、调用前先重置计数器，让每一次改动都能扛住最糟时刻的崩溃。

一个只读的 agent 很容易做可靠，最坏情况就是重跑一遍。一个会花钱的 agent（花钱、花配额、花限速 API 的预算），或者一个会改共享状态的 agent，才是顺序 bug 藏身的地方。这一篇讲几条排序规则，它们决定了在最糟糕的那一瞬间崩溃，是让你亏钱、还是让你保持干净。

这些规则都不聪明。它们无非是"在正确的顺序上保持偏执"。

昂贵步骤问题#

设想一个要花真金白银的步骤：它调一个昂贵的模型、生成一段视频、跑一个长任务。用户有配额。天真的流程是：

1
2

1. 做那件昂贵的事
2. 成功后，扣配额

这种错只在规模上来后才现形。第 1 步和第 2 步之间，什么都可能发生：进程崩了、网断了、用户请求超时后重试。现在你做了那件昂贵的事（花了真钱），却从没为它收过费。这么干一千次，你就在给陌生人的算力买单。

反过来：

1
2
3

1. 原子地预留 / 扣掉配额
2. 做那件昂贵的事
3. 失败时，退款

现在第 1、2 步之间崩溃，代价是用户损失一笔可退的预留，而不是你损失一块真钱。在承诺的那一刻扣费，不是在成功的那一刻。 你想要的故障模式是"用户为一件没完成的事付了费，我们退给他"（烦，但可恢复），而不是"我们干了没人付钱的昂贵活儿"（那是无声的利润流血，账单来之前你根本不会发现）。

退款那条路（第 3 步）不是可选项。如果你预先扣费，就必须在真实失败时退款，否则你只是把这份不公平转嫁给了用户。先扣费再产出，只有和可靠的失败退款配对才成立。

在调用前重置计数器，不是调用后#

一个近亲。假设你有个尽力而为的机制，放弃之前允许 N 次尝试：一个重试预算、一个"重新生成"额度、一个 fallback 计数器。你在哪儿重置这个计数器？

直觉是在一次成功调用之后重置（“我们成功了，清掉失败计数”）。这是个微妙的 bug。如果重置发生在调用之后，而崩溃的恰恰是这次调用，那计数器永远不会重置，于是下一次调用就带着一个中毒的计数开始，继承了一个早已结束的运行留下的失败。

在调用之前重置：

1
2
3

1. 把计数器重置到干净状态
2. 发起调用（内部重试时它可能自增）
3. （这里不要重置）

原则是：在拥有某个状态的那次操作的开头去初始化它，而不是在上一次操作的结尾。 “成功时"清理的状态，一旦成功没发生就会泄漏，而你之所以有个失败计数器，正是因为成功并不总会发生。干净的状态是你去建立的前提，不是你去赏赐的奖励。

每次改动都要有撤销标记，每条读路径都要认它#

第三条规则是关于那些你可能需要回滚的改动。当一个 agent 写下某样后续步骤可能作废的东西（一条投机记录、一份草稿、一个预留的名额），别只是写下去。写的时候带一个标记，说"这是临时的 / 这个已被撤销”，并且让每一条读路径都对这个标记做过滤。

陷阱是不对称。你很容易在写入侧和主读路径加上标记，然后忘掉另外三个也在读这份数据的地方：一个导出、一个后台视图、一个聚合计数、一个二级索引。那些没过滤的读者，会兴高采烈地把你以为已经撤回的数据端上来。撤销于是变成了谎言：一个视图里撤了，另外四个里还活着。

所以这条规则要刻意说成一个整体：如果一次写入可以被补偿，那么对这份数据的每一次读取都必须对补偿标记做过滤。 不是大部分读取。是每一次。以后你加一条新读路径时，对标记过滤是写这条读路径的一部分，就像给查询做参数化是写 SQL 的一部分。只要有一个读者忘了，你的"撤销"就悄悄不再是撤销。

靠身份幂等，不靠计数#

三条规则底下的连接组织是幂等：同一个操作跑两遍，和跑一遍得到一样的结果。崩溃和重试一定会让你的步骤跑不止一次。如果重复的步骤会重复扣费、重复写入、重复推进，你就有一个 correctness bug 在等一个倒霉的日子。

拿到幂等的可靠办法，是让操作以稳定的身份为键，而不是以计数或顺序为键。 “为请求 abc-123 扣费"是幂等的：第二次尝试发现那个 id 的扣费已经存在，什么都不做。“从余额里减一"不是：第二次尝试又减一遍。“插入自然键为 X 的行"是幂等的；“追加一行"不是。

当我去清理或对账状态时（尤其是让一个 agent 半自主地做），我从不说"删掉最后 N 条"或"移除多出来的”。我按精确记录的 id 去删：操作精确记下了它创建了哪些 id，撤销就恰好移除那些，绝不靠推断。推断（“多了 3 条，删 3 条”）正是自主清理删错东西的原因。这整个是后面一篇的主题。

心智模型#

四条规则塌缩成一个习惯：假设进程在最糟糕的那一行死掉，然后问自己你被留在了什么状态。 在扣费和产出之间？可退，没事。在产出和扣费之间？你刚白送了钱，把顺序调过来。计数器在一次崩溃的调用之后才重置？下一次运行中毒了，把它挪到前面。一条读路径忘了撤销标记？你的撤回是假的，去把它做成整体的。

大部分 agent 工作不需要分布式系统那套机械。你需要的，是把改动写成一个"半路崩溃"很无聊的顺序，并且让一切以身份为键，好让重试免费。
