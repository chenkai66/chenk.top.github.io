让 Agent 靠谱起来（5）：让自主不会删错东西

自主清理和自愈，正是 agent 的全部意义，也是删错数据最快的路。解法：只对精确记录的身份动手、任何破坏性步骤之前拿计数和现实核对、信任一个信号之前先审问它。

Read in English →

前四篇讲的是验证，证明活儿真的发生了。这一篇讲相反的风险：让一个 agent 自己去做破坏性动作，然后它自信地毁掉了不该毁的东西。

自主是构建 agent 的全部理由。一个每个动作都得请示的 agent 不是自动化，是一个多了几道手续的慢人类。但自主的故障模式格外糟：一个删错行的人类通常会察觉然后停手；一个在执行计划的 agent 会高高兴兴地删掉错的那行、然后下一行、再下一行，以机器的速度、带着彻底的自信。

所以问题不是"自主还是不自主"。是"我怎么让它在安全操作上自由行动，同时让破坏性操作几乎不可能出错"。

按记录的身份删，绝不按推断#

自主破坏性动作最重要的一条规则：只对精确的、记录下来的身份动手，绝不对推断出来的数量或位置动手。

危险的模式看着挺合理：“好像多了三条记录，那就删三条。“或者"移除最近的 N 条”。或者"清理重复项”。这里每一个都是关于"哪些是错的项"的推断，而推断恰恰是 agent 会搞错的东西：一个竞态刚加了一条真实记录，你现在把它数成"多出来的"；一个排序变了；你对"重复"的定义太松。

安全的模式，是让那个创建的操作精确记下它创建了什么（那些确切的 id），让撤销操作恰好移除那些、不算任何东西。一个步骤插入记录时，就把它们的 id 写下来。清理跑起来时，就删那些特定的 id、且只删那些。不数数，不管"多出来的"，不管"最近的"。撤销是对一个记录下来的事实的重放，不是一次新的判断。一个 agent 可以完全自主地跑它，因为已经没有留给它去搞错的推断了。

扣扳机之前，拿计数和现实核对#

哪怕用了基于身份的删除，在任何破坏性动作触发之前，也加一道现实核对，一道信任但验证的门。

删之前，agent 应该确认它即将删的东西和它的预期相符：它记录的记录条数和它即将移除的条数相符、那些 id 仍然存在、仍然长得像它创建的东西、目标集合里没有冒出意料之外的东西。如果现实和计划不符（数量对不上、某个 id 指向的东西和记录的形状不匹配），agent 应该停下来把它抛出来，而不是继续。

这是针对"‘定计划’和’执行计划’之间世界变了"这种情况的廉价保险。并发活动、上一次跑到一半、期间有人手工改了一下，这里任何一个，都能让一个成形时正确的计划、在执行时变得危险。现实核对抓的就是这个漂移。规则是：一个破坏性计划是关于当前状态的一个假设；在动手之前，立刻拿这个假设和现实对一遍。

信任一个信号之前，先审问它#

再上一层：自动化系统基于一个信号决定去采取补救动作，一个监控去重启服务、一个扫描器去标记并修复、一个 autopilot 从队列里挑活儿去应用。

这里的陷阱是基于一个低质量的信号动手。一个监控看到内存高就杀进程，但正如第一篇所说，构建 finalize 阶段的内存高是健康的，杀掉它就毁了好活儿。信号（“内存高”）是真的；解读（“所以出问题了”）是错的，因为这个信号没能区分"健康地忙"和"真的卡住"。

在一个自动化系统采取破坏性或纠正性动作之前，它必须审问这个信号，把良性的成因和恶性的成因分开。 就内存这个例子：进程在某个别的轴上有进展吗（文件在写、CPU 在有效地忙）？有，那内存高是预期的负载，别动它。没有（输出停滞、资源崩塌），那是真麻烦，动手。一个数字很少足以正当化一个破坏性动作；你需要足够的信号，才能把这个数字的好成因和坏成因分开。

同样的纪律适用于任何自动修复：别把一个动作接到单一阈值上。把它接到一个诊断上，一组真正能把"动手有帮助"和"动手有害"分开的信号组合。

让读和分析自主，给写加门#

合起来，行得通的实用划分是：

  • 读、搜、分析、规划：完全自主。 这些是可逆的（最坏就重跑），可以安全并行。当我把活儿铺给子 agent 时，子 agent 是只读的：它们调查、benchmark、审计、提议。让它们自由跑。
  • 写、删、改共享状态：加门。 由母 agent（或单一串行的执行者）来做这些改动，用记录的身份，任何破坏性动作之前先做现实核对，应用之后再按前几篇说的那样验证真实结果。

这个划分给了你几乎全部的自主速度（昂贵的、可并行的那部分——调查——自由跑），同时把不可逆的那部分拴在短绳上。子 agent 可以又多又大胆，因为它们什么都弄不坏。那个能弄坏东西的唯一执行者小心地走，走在记录的身份上，每个破坏性步骤之前先和现实对一遍。

自主和安全在这里不是对立的。你两个都要，办法是对可逆的活儿自主、对不可逆的活儿偏执，并且永远不让一个 agent 去推断该做哪件不可逆的事。

接下来的内容#

下一篇讲一个吃复利的习惯：每次一个修复落地，把之前的修复也重新验证一遍。长期运行的系统会积累退化，一个新改动悄悄破坏了一个旧保证。模式叫分层验证，每一轮都在真实触发路径上重新检查前面几轮，好让旧修复没法悄悄烂掉。
