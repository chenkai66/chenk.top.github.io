让 Agent 靠谱起来（1）：构建，才是唯一的验收门

当你让一群 agent 去改真实代码，每个 agent 都会告诉你它那块编译通过了。但这不是关键。唯一的验收标准，是整个系统还能不能构建、能不能跑起来。

我跑过很多长期运行的 agent 循环：母 agent 派子 agent，每个子 agent 改代码库的一小块，最后母 agent 把结果拼回去。这些年我学到的最贵的一课，说出来简单得让人尴尬：一个组件报告"绿了"，几乎不能说明整个系统能不能用。

这是关于如何让这类系统保持诚实的七篇笔记的第一篇。它们都刻意写得通用，不依赖某个具体框架或模型。这一篇是后面六篇的地基。

故障长什么样：每块都绿，整体是坏的#

灾难的形状是这样的。母 agent 派出三个任务。每个子 agent 改自己那几个文件，跑一遍本地检查——对改动文件做类型检查、给自己模块跑单测，看到绿了，就报成功。母 agent 收到三个"完成"，宣布胜利。

然后你真的去构建，它编译不过。

怎么会？某个子 agent 加了个 import，单独看没问题，但和另一个子 agent 重命名过的符号撞了名。一个共享接口在一个文件里多了字段，在另一个文件里又少了字段。一个 agent 删掉的配置项，三个模块之外还在被引用。每个子 agent 局部都对，集成起来全局就崩了。而且因为每个子 agent 只检查了自己那一块，没人在看故障真正发生的那条缝。

阴险的地方在于，这些 per-agent 检查并没有错，它们只是在回答一个比真正重要的问题更窄的问题。“我的文件类型检查过了吗"不等于"整个项目能构建吗”。这两个问题之间的落差，恰恰就是多 agent 协作最容易翻车的地方。

规则：母 agent 的真实构建，才是验收门#

所以我现在雷打不动地守着一条规则：

唯一算数的信号，是母 agent 在所有改动都落地之后，端到端地跑一次真实构建加真实冒烟测试。 Per-agent 的检查只是提示，不是验收。

具体来说，母 agent 的工作流是这样：

1
2
3
4
5

1. 派子 agent，收集它们的 diff
2. 把所有 diff 应用到同一个工作树
3. 跑真实的生产构建命令
4. 跑一个最小冒烟测试（服务能起来吗？一个真实请求返回 200 吗？）
5. 到这一步，这一批才叫"完成"

第 3、4 步不容商量，而且它们属于母 agent，不属于子 agent。子 agent 没法验证集成，因为子 agent 看不到集成。只有母 agent 手里握着合并后的状态，所以也只有母 agent 能测它。

写下来显得理所当然。可实践里，“相信子 agent"的引力很强：它们就在那儿告诉你成功了，而重跑一次完整构建又慢又有时痛苦。这股引力就是陷阱。

为什么"又慢又痛苦"不是借口#

最常见的反驳是成本。完整构建很慢。在一台内存紧张的机器上，一次构建可能 thrash 二十分钟，甚至直接倒下。改动"明显安全"的时候，跳过它总行吧？

不行。但你可以在批量上做文章。

诀窍是把验收门的频率和改动的频率解耦。别每改一次就构建一次，攒几个改动，付一次构建的钱。 如果四个 agent 各自做了一个小的、只动 prompt 的改动，那就四个一起应用，然后只构建一次。你把验收门的成本摊到整批上，而不是每个改动都付一遍。

绝对不能做的，是因为这一批"感觉安全"就跳过验收门。集成 bug 之所以危险，正是因为从任何单个改动内部看，它都不危险。那种安全感，是盯着一小块看出来的；而 bug 就住在你没在看的那条缝里。

还有第二个理由让你即使构建很贵也要尊重它：脆弱的构建本身就是信号。如果你的验收门老是倒下，那是在告诉你系统耦合太紧、或者资源不够。靠跳过验证把它糊过去，只是把故障推到下游，在那儿更贵、更难找。

区分"慢构建"和"卡死的构建”#

如果你要拿构建当验收门，就得会分辨"慢"和"卡死"，否则你会因为没耐心而杀掉健康的构建，然后照搬一套没用的重启仪式。

在一台资源紧张的机器上，我看三个信号来区分：

  • 健康的慢构建：一个 worker 进程把 CPU 打满，swap 用量低且稳，关键是输出目录最终会随着编译器进入 finalize 阶段而文件暴涨。这看着吓人（好几分钟什么都看不到），但它在干活。忍住，等它。
  • 真正卡死的构建：零文件写入，swap 稳步往天花板爬，可用内存崩塌。那是 thrash，不是进展。杀掉它，回收资源，给足头寸再重试。

通用原则是：在你插手一个长时间运行的步骤之前，先量清楚它到底在干什么。 “它跑了挺久了"不是诊断。看它是不是在某个可观测的轴上有进展（文件在写、CPU 在有效燃烧、日志在往前走）。因为没耐心而杀掉健康的工作，本身就是一种可靠性 bug。

给确定性代码一道更便宜的门#

构建是集成的验收门。但有些改动动的是纯确定性逻辑——一个规则引擎、一个扫描器、一个解析器、一个打分函数。对这类改动，值得在昂贵的构建之前加第二道更便宜的门。

我改一个确定性函数时，会当场跑一个极小的自测：喂它三个已知输出的输入。

  • 一个应该触发行为的输入（真阳性）
  • 一个在不该触发的上下文里的输入（带守卫的假阳性）
  • 一个正好命中我刚加的东西的输入（新分支）

这能抓到逻辑回归（一个变得过度积极的守卫现在把真命中也压掉了、一条新规则永远不触发），比完整构建快得多，也比类型检查精确得多。类型检查只证明代码形状对，不证明它正确。类型检查告诉你形状对了；三例自测告诉你行为对了。对确定性代码来说，咬你的是后一个问题。

贯穿始终的那条线#

后面六篇笔记，某种意义上都是这一篇的变奏。Agent 系统的可靠性，几乎从来不是靠把某一步做得更聪明。它靠的是对"什么才算完成"保持纪律：拒绝用一个更窄、更便宜的信号去顶替那个真正的信号，哪怕真的那个又慢、哪怕每一块都发誓自己没问题。

子 agent 永远会告诉你它成功了。作为母 agent，你的活儿就是——在整个东西构建并跑起来之前，别信它们。

接下来的内容#

下一篇讲的是这个问题的镜像：当你的验收信号本身不靠谱时怎么办。那个告诉你"可见了"“完成了"的东西，可能是一个偶尔会悄悄撒谎的概率型观察者。答案是确定性的兜底网，它帮我躲掉的隐形故障，比任何别的东西都多。
