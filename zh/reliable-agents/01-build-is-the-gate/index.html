让 Agent 靠谱起来（1）：构建，才是唯一的验收门

三个 agent 各改一个 TypeScript 仓库的一块，各自跑 tsc 都通过，各自报成功。合并后的代码八秒就编译失败。修法只有一条规则：只有母 agent 的整体构建才算完成。

#agents#reliability#verification#orchestration
Read in English →

上个月一次三 agent 的任务，最后留给我一个编译不过的仓库，而里面每个 agent 都报告了成功。这个矛盾，就是这篇要讲的全部。

场景很普通。母 agent 把一次重构拆成三个任务，各交给一个子 agent。子 A 把一个共享类型挪进了新模块。子 B 重命名了那个类型引用的一个函数。子 C 删了一个配置字段，而三个文件之外还有地方在读它。每个子 agent 对自己改过的文件跑了 tsc --noEmit，没报错，于是返回 {"status": "done"}。母 agent 收到三个 done，就往下走了。

然后我跑了真正的构建：

$ pnpm build
src/pipeline/stage.ts:42:18 - error TS2305: Module '"../types"' has no exported member 'StageResult'.
src/config/load.ts:7:9 - error TS2339: Property 'maxRetries' does not exist on type 'Config'.
Found 2 errors in 2 files.

两个错误，落在两个文件里，而没有任何一个子 agent 同时改过这两处。子 A 的搬移和子 B 的重命名，各自单看都对，错在两个改动的交界处。而这个交界处没人管：它不属于任何一个子 agent，所以没有一个子 agent 会去检查它。

子 agent 报"绿"，为什么没那么值钱#

一个子 agent 对自己的文件跑 tsc，回答的是一个真问题：我这块内部自洽吗？但它回答不了决定这次任务成败的那个问题：合并后的代码能编译吗？只要两个改动一交互，这两个问题就分家了——一个被重命名的导出、一个被删掉的字段、一个单独能解析、合并后却撞名的 import。

这不是子 agent 的错。每个都精确做了被要求的事。落差是结构性的：没有子 agent 看得见合并后的状态，所以没有子 agent 能验证集成。 问一个子 agent 项目能不能构建，是在问它一个它根本观察不到的世界。

那条规则#

只有一个信号算"完成"：母 agent 把每个子 agent 的 diff 都应用到同一个工作树之后，端到端地跑一次真实构建和一次真实冒烟测试。

3
4
5

1. 收集每个子 agent 的 diff
2. 把所有 diff 应用到同一个工作树
3. 跑生产构建命令（tsc / pnpm build / cargo build …）
4. 跑一个最小冒烟测试：服务能起来吗？一个真实请求返回 200 吗？
5. 到这一步，这一批才叫"完成"

第 3、4 步属于母 agent，不属于子 agent，理由和那个 bug 一样：只有母 agent 握着合并后的状态。子 agent 的检查仍然有用，它能在一块自身就坏了的时候提前拦下，省掉一次白跑的构建。但那是预筛，不是验收门。

成本这个反对意见，以及诚实的回答#

真实构建很慢。我跑其中一条管线的那台 3.4 GB 小机上，一次 Next.js 构建要三到二十分钟，偶尔还 OOM。所以每当一批改动"看起来安全"，跳过构建的诱惑就很强。我妥协过，也为此付过代价。

解法不是跳过验收门，而是挪动它。把验收门的频率和改动的频率解耦：如果四个 agent 各做了一个只动 prompt 的小改动，那就四个一起应用，只构建一次。你把一次构建的成本摊到整批上，而不是每个改动付一遍。绝对不能做的，是因为这批"感觉安全"就跳过构建。集成 bug 的危险就在这里：站在任何一个改动内部看，它都不危险。那份安全感来自只盯着自己这一小块，而集成 bug 恰恰是单看一块时看不见的那种问题。

尊重一个昂贵构建还有第二个理由：老是倒下的构建，本身就在告诉你事情。如果验收门隔一次就 OOM，说明系统耦合太紧或者资源不够；跳过验证只是把这个故障挪到一个更贵、更难找的地方。

分清"慢构建"和"卡死的构建"#

拿构建当验收门，就得会分辨"慢"和"卡死"，否则你会因为没耐心杀掉健康的构建。在那台紧张的小机上，我看三个信号：

  • 健康但慢：一个 worker 把单核打满，swapUsed 低且平，而最决定性的一点是，.next 输出目录最终会在六十秒内从个位数文件暴涨到约 1800 个，那是编译器进入 finalize 阶段。好几分钟什么都看不到，然后一阵猛写。忍住，等它。
  • 真卡死：零文件写入，swapUsed 稳步爬过 1.7 GB 往天花板去，可用内存崩到约 100 MB。那是 thrash，不是进展。杀掉它，swapoff -a; swapon -a 回收，给足头寸再重试。

一般形式是：在你插手一个长步骤之前，先在某个可观测的轴上量清楚它在干什么：文件在写、CPU 在烧、日志在往前走。“它跑了挺久了"不是诊断，而因为没耐心杀掉健康的活儿，本身就是一种可靠性 bug。

给确定性代码一道更便宜的门#

构建把守的是集成。但有些改动动的是纯函数：一个规则引擎、一个扫描器、一个打分函数。对这类改动，完整构建杀鸡用牛刀，而类型检查又太弱，它只证明形状能编译，不证明逻辑是对的。所以我在构建之前先跑一个三例自测：

# 一个扫描广告法绝对化用语的合规扫描器
assert scan("全网最低价") == ["最低价"]      # 真阳性：必须命中
assert scan("最高人民法院发布") == []          # 带守卫的假阳性：绝不能命中
assert scan("国家级资质") == ["国家级"]        # 我刚加的那条新规则

最后一行才是关键：自测要带上你刚改的那个 case。它能抓到一个变贪了的守卫（现在把真命中也压掉了），或者一条永不触发的新规则——这些都是类型检查一路放行的回归。对确定性代码来说，咬你的问题是"它在已知输入上行为对不对”，而这个问题回答起来很便宜。

接下来的内容#

构建是一道你能掌控的门。更难的情况是：那个本该告诉你"某件事成了"的信号，本身就不可靠：一个悄悄没触发的 IntersectionObserver、一个把自己的输出判为完成的 LLM。下一篇讲怎么给一个概率型触发器垫一层确定性后盾，它帮我躲掉的隐形故障比这里任何东西都多。
